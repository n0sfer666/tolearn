# ADR-006. Вердикт практики выносит человек, не программа

У практики **две** независимые коллекции проверок, и путать их нельзя:

| | Смысл | Куда идёт |
|---|---|---|
| `practice.constraints[]` | ограничения на форму решения: «клиент содержит ровно один base_url и ни одного литерального ключа» | плейсхолдер `{{practice.constraints}}` |
| `practice.acceptance[]` | приёмка результата: «клиент ходит через шлюз и получает ответ, валидный по своей же схеме» | плейсхолдер `{{practice.acceptance}}` |

Обе имеют одинаковую форму `{id, claim, check, expect}` и обе отображаются на
экране практики. Разделены они не случайно: ограничение можно нарушить, получив
работающий результат, и это разные разговоры на зачёте.

Поле `expect` в обеих написано прозой:

> `constraints[].expect: Первое число не меньше 10, второе не меньше 3.`
> `acceptance[].expect: Печатается SCHEMA_OK, исключения нет.`

Автоматически такое не проверить — и попытка была бы враньём. Поэтому раннер
показывает вывод команды рядом с ожиданием, а отметку ставит человек.

Отдельно: `check` — это произвольный shell, сочинённый языковой моделью. В
эталоне встречается `cd` с записью файлов и `npx promptfoo@latest eval`,
скачивающий пакет из сети. Он **никогда** не выполняется автоматически: только
по явному нажатию, с показом полного текста команды до запуска. Флаг
`smoke_checked: false` — прямое заявление генератора «эту команду никто не
запускал» — показывается рядом с кнопкой.
