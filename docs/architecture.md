# Архитектура

Ограничения, из которых всё следует, карта решений и числа, которыми они
проверяются. Каждое решение живёт отдельным файлом в [`adr/`](adr/): одно
решение — один документ, с альтернативами, которые были отвергнуты, и с
условием, при котором его следует пересмотреть.

## Ограничения, из которых всё следует

1. Приложение не имеет права требовать сеть для основной работы.
2. Приложение не имеет права требовать аккаунт, ключ или оплату.
3. Бандл обучения генерируется снаружи и может быть перегенерирован в любой
   момент. Всё, что создал пользователь, обязано это пережить.
4. Файлы бандла написаны LLM. Они могут быть неполными, невалидными и содержать
   произвольные shell-команды.
5. Размер и скорость — функциональные требования, а не пожелания.

## Бюджеты

Ограничение 5 бессмысленно без чисел — DoD, который нельзя провалить, не DoD.
Пороги фиксируются в тестах и ломают сборку при превышении:

| Что | Порог |
|---|---|
| Установщик, macOS arm64 | ≤ 12 МБ |
| Установщик, Windows x64 | ≤ 14 МБ |
| Установщик, Linux x64 | ≤ 14 МБ |
| JS на странице темы (сжатый) | ≤ 30 КБ |
| JS на странице списка программ (сжатый) | ≤ 15 КБ |
| JS на странице графа зависимостей (сжатый) | ≤ 60 КБ |
| JS на любой другой странице (сжатый) | ≤ 20 КБ |
| Открытие темы среднего размера, от нажатия до готового текста | ≤ 150 мс |
| Импорт эталонного бандла (7 тем) | ≤ 300 мс |
| Холодный старт до списка программ | ≤ 800 мс |
| Веса распознавания речи (`-with-speech`) | ≤ 192 МБ |
| Расшифровка минуты речи (`-with-speech`) | ≤ 60 с |
| Ошибка распознавания на корпусе `fixtures/audio/` | ≤ 5 % слов |

Потолок установщика — общий: расширения его не расширяют. Всё, что добавляют
zip/tar (S48) и age (S53), укладывается в те же 12–14 МБ, и если не
укладывается — режется функция, а не порог.

`-with-speech` в потолок установщика не входит: его вес определяют веса модели, и
три строки выше назначены замером S55 на `ggml-small-q5_1` (ADR-010). Держит их
`speech/tests/corpus.rs` — он же печатает измеренные числа. Тест идёт под фичей
`speech` и пропускается, когда весов нет: путь к ним задаёт
`TOLEARN_WHISPER_MODEL`, скачивает их отдельный шаг джобы `-with-speech`.

Строка про время назначена железу пользователя. Общая виртуалка CI под неё не
подходит — на четырёх vCPU расшифровка идёт медленнее реального времени, — и
раннер объявляет себя такой машиной через `TOLEARN_SPEECH_SHARED_CPU`: замер
печатается, но не проверяется. Порог от этого не меняется, меняется место
замера; на Linux и Windows его снимает человек на живой машине
([checks.md](../.context/checks.md)).

Числа взяты как заведомо достижимые для выбранного стека и подлежат ужесточению
по факту замеров, а не ослаблению.

## Структура

```
core/       Rust: типы, парсинг, валидация, прогресс, статусы, протокол
runner/     Rust: исполнение check-команд       (зависит от core)
offline/    Rust: загрузка, архивация, кэш      (зависит от core)
provider/   Rust: настройки LLM, ключ, проверка (зависит от core, runner)
gestures/   Rust: нативный жест «назад»         (ни от чего не зависит)
speech/     Rust: микрофон и whisper.cpp        (ни от чего не зависит)
cli/        Rust: tolearn validate|scan|exam    (зависит от core, runner, offline)
app/        Tauri 2: IPC, окна, пререндер       (зависит от нижних слоёв)
ui/         Astro + Solid                       (общается только через IPC)
docs/       решения, спецификации, контракты
examples/   эталонные бандлы, они же фикстуры
fixtures/   ветки, которых нет в эталоне: валидные и битые документы
```

Направление зависимостей — только вниз. `core` не знает про Tauri, файловый
диалог и UI; `offline` не знает про Tauri (ADR-003). CLI существует не для
пользователей, а чтобы каждый слой можно было прогнать в тестах и в CI без GUI.

`gestures` стоит особняком: это единственное место, где разрешён `unsafe`.
Нативный жест «назад» включается свойством платформенного вебвью, а указатель на
него сырой — держать такой вызов в `app` нельзя, там `unsafe_code = "forbid"`,
как и во всех остальных крейтах. Крейт ни от чего не зависит, наружу отдаёт одну
функцию и на системах без такого жеста не делает ничего.

Это дерево базового варианта, и S01 заводит именно его. Расширения приносят свои
единицы и объявляют их в своих спеках: распознавание речи (S55), плагин
Obsidian отдельным пакетом (S54). Направление зависимостей на них
распространяется без исключений.

## Представление бандла

Бандл приходит в **одном** формате: генератор кладёт либо `.json` (по
умолчанию), либо `.yaml` (по запросу), двойников рядом не оставляет. Если
двойники всё же лежат рядом (старый бандл, ручная копия), приложение не
отказывается импортировать, а берёт `roadmap.yaml`: формат решает и то, какой
файл прогресса ведётся, а правит руками человек именно YAML.

Приложение читает оба формата одним парсером: JSON — подмножество YAML 1.2, и
разбор `roadmap.json` даёт ту же структуру, что разбор `roadmap.yaml`
(закреплено тестом `core/tests/json_twins.rs`). Формат — вопрос выбора файла на
входе, не вопрос разбора: дальше по коду едет уже разобранный документ.

Схем в бандле три, и версии у них независимые: `learning-roadmap/v1` (roadmap),
`learning-roadmap/topic/v1` (темы), `learning-roadmap/progress/v1` (прогресс).
Несовпадение мажорных версий между файлами одного бандла — ошибка импорта, а не
повод угадывать.

Контракт записан в [`schemas/`](schemas/) — по файлу на схему, JSON Schema
draft 2020-12, без внешних `$ref`: схема читается и проверяется без сети. Каждый
объект в каждой схеме закрыт `additionalProperties: false`, иначе утверждение
«схема описывает все поля эталона» нечем доказать. Роль каждого описанного поля
(рендерится, влияет на логику, игнорируется) зафиксирована в
[`fields.md`](fields.md), корпус документов — в [`fixtures/`](../fixtures/).

Схема темы длиннее двухсот строк (211) и остаётся одним файлом: это один
неделимый контракт одного документа, который читается сверху вниз, а разрезать
его пришлось бы по `$defs` — то есть по механике JSON Schema, а не по границе
смысла. Дробление контракта на файлы вернуло бы внешние `$ref` и вместе с ними
загрузчик — ровно то, от чего избавляет самодостаточность схемы.
